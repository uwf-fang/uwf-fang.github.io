Connecting Problem Types to Algorithm Paradigms

Use a small finite packing example to distinguish what a problem asks from how an algorithm solves it. Enumeration is one useful conceptual model, not a required first step.

1. The Pipeline Model: One List, Five Questions

For this finite packing example, imagine filtering all subsets to obtain valid choices. We can ask different questions about that same solution space. An actual search, decision, or optimization algorithm need not generate or store this complete list.

Stage 1: All Combinations
Every Theoretical Choice (16 Possibilities)

Every theoretical combination of items. Many of these break the rules (e.g., exceeding the maximum bag weight).

↓ Filter out choices that break the rules
Stage 2: The Central Hub
ENUMERATION ("Find All Valid Options")

The complete collection of choices that follow every rule. For this example, each question refers to the same feasible choices:

↓ What do you want to do with this list?
Take First Match

SEARCH

"Just hand me any valid solution."
Stops immediately as soon as 1 satisfying item is found.

Is List Empty?

DECISION

"Is there at least one valid solution?"
Answers strictly YES or NO.

Count Items

COUNTING

"How many valid choices are there?"
Tallies the total without needing to store each item.

Pick The Best

OPTIMIZATION

"Which one of these has the highest score?"
Returns a feasible solution with the best objective value; full enumeration is only one possible method.

2. See It in Action: The Packing Problem

Suppose you are packing a bag. Your bag can hold a maximum weight of 5 kg. You have 4 items to choose from:

Items available: Water Bottle (3 kg, $10) • Book (2 kg, $4) • Snack (1 kg, $3) • Camera (4 kg, $9)

Problem to solve

List every subset with total weight ≤ 5 kg, including the empty bag.

Choose each item at most once. A combination can contain several items. The empty bag counts as one combination in enumeration and counting.

The Valid Options List (Weight ≤ 5 kg)

9 Valid Combinations
Enumeration outputs every single combination of items that does not exceed 5 kg.

3. The Catch: Why Not Always Use Enumeration?

If we can solve this small finite example by generating the full list and inspecting it, why do we need algorithm paradigms?

The Bottleneck: Combinatorial Explosion

With 4 items, there are only 16 choices. But with 50 items, there are over 1,000,000,000,000,000 candidate choices. The number of subsets grows exponentially; even a simple scan becomes impractical as the item count increases.

Algorithmic paradigms are shortcuts that answer Decision, Search, Counting, or Optimization questions without ever generating the whole list.

Paradigm How It Avoids the Full List What It Solves Best
Brute Force Does not avoid it. Exhaustively visits every single choice one by one. Small toy problems
Backtracking Builds solutions step-by-step. The moment a rule is broken (e.g., bag exceeds 5 kg), it stops and turns back immediately, ignoring that entire branch. Search • Decision • Enumeration
Branch & Bound Tracks the best score found so far. If an incomplete branch cannot mathematically beat the record, it abandons the branch immediately. Optimization
Dynamic Programming Recognizes repeated subproblems, such as the same next item index and remaining capacity. It solves that subproblem once, saves the result, and reuses it. Optimization • Counting
Greedy Commits to a locally chosen option. A correctness argument can make it exact (Huffman coding, nonnegative-weight Dijkstra); other greedy choices are heuristics. Exact when justified; otherwise a heuristic
Divide & Conquer Splits a problem into smaller subproblems, solves them recursively, and combines their results. The split and combination depend on the problem. Counting • Math Evaluation

4. Examples, assumptions, and counterexamples

A paradigm does not impose a universal compatibility rule. These examples illustrate useful fits; analyze the specific problem before choosing a method.

ParadigmExample useCondition or limitation
Brute forceEnumerate subsets, count feasible choices, or select an optimumExact for a finite exhausted search space, but may be expensive
BacktrackingN-Queens search, decision, enumeration, and countingPrune only when no valid completion can extend the partial state
GreedyHuffman coding; Dijkstra; packing heuristicsExactness needs a correctness argument; Dijkstra requires nonnegative weights
Divide and conquerBinary search, merge sort, maximum subarrayInclude the cost and correctness of combining subproblem answers
Dynamic programmingLCS, matrix-chain optimization, counting pathsThe state must capture everything needed for the remaining subproblem
Branch and boundOptimization over a finite search treeA valid bound rules out branches that cannot improve the incumbent
